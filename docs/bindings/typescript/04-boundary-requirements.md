# 04 · Requirements on the boundary

This is the contract between this plan and the porting plan. The boundary itself is designed in
[`docs/porting/`](../../porting/); this list says what the TypeScript binding needs from it, and
why. Every requirement is phrased for any host language, not just TypeScript: if a requirement
only helps TypeScript, it does not belong in the boundary and the binding handles it on its side.

All fifteen were sent to the porting-plan thread on 2026-10-29, and
[`docs/porting/bindings.md`](../../porting/bindings.md) answers each by number. The boundary
crate is `crates/abi` (`shallot-abi`).

## How the binding uses the answers

- **Change marking (R2).** The boundary marks writes made through a column view with
  `column_mark(world, component, field, eids, count)` rather than exposing the dirty bitsets. The
  facade's `.set(eid, …)` therefore writes the value straight into the view and appends `eid` to a
  per-field scratch list in TypeScript; the list is flushed with one `column_mark` call when the
  current TypeScript system returns, and before any `world_step`, `world_tick` or `app_frame`.
  That keeps hot-path writes free of boundary calls and costs one call per touched field per
  system.
- **The loop (R7).** Bun never calls `app_run`, which blocks the JavaScript event loop. It calls
  `app_frame` in the pumped loop from [02-runtimes.md](02-runtimes.md#the-frame-loop-on-native).
  The porting plan confirms that `app_frame` services the engine's own window on native, not only
  a browser's `requestAnimationFrame`.
- **Handles.** Handles and entity references are `u64`, which `bun:ffi` and wasm both surface in
  JavaScript as `BigInt`. The facade converts them to `number` where they fit in 53 bits (index
  plus a generation of 21 bits or fewer), so `materials.add(...)` keeps returning a `number` as it
  does today. The porting plan fixes handles and entity references at 53 bits or fewer (a 32-bit
  index plus a wrapping generation of at most 21 bits), so this always holds.

## Things the binding deliberately does not need

- **Per-entity accessor functions** such as `get_f32(world, component, field, eid)`. They would
  exist for languages without shared memory, but TypeScript must not use them on hot paths.
- **Host-allocated component storage.** The engine owns all ECS memory.
- **Callbacks from worker threads.** See R12.
- **A C header.** The TypeScript glue is written against the Rust definitions and the reflection
  dump.
